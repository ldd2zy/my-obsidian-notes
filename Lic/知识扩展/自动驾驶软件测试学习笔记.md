# 一、软件测试的基本概念

## 1.1 什么是软件测试

软件测试就是检查代码在不同输入情况下，能否按照预期正确运行。

例如：

自动驾驶系统中存在以下功能：

- GNSS 坐标转换
- 障碍物过滤
- TTC 碰撞时间计算
- 路径规划
- PID 速度控制
- 自动停车决策

这些功能组合起来构成完整的自动驾驶系统。

软件测试就是分别检查这些功能，以及它们之间的配合是否正确。

## 1.2 软件测试的主要类型

| 测试类型 | 测试对象 | 测试目的 | 自动驾驶案例 |
|---|---|---|---|
| 单元测试 | 单个函数、类 | 验证独立功能 | TTC 计算是否正确 |
| 集成测试 | 多个模块 | 验证模块之间的通信和协作 | 感知能否将障碍物传给决策 |
| 系统测试 | 完整系统 | 验证整体功能 | 自动驾驶车辆能否完成任务 |
| 回归测试 | 修改后的软件 | 验证旧功能没有被破坏 | 修改障碍物过滤后重新测试 |
| 实车测试 | 真实车辆 | 验证实际运行效果 | 车辆遇到障碍物能否安全停车 |

## 1.3 三种测试的区别

以自动停车为例：

**单元测试：**

给 TTC 函数输入距离和相对速度，检查计算结果是否正确。

**集成测试：**

模拟雷达发现障碍物，检查感知、决策、控制模块能否完成数据传递并发出停车命令。

**系统测试：**

在完整车辆系统中验证车辆是否能够真正减速并停止。

三种测试是递进关系，不能相互替代。

# 二、单元测试（Unit Test）

## 2.1 什么是单元测试

单元测试是针对一个独立的代码单元进行测试。

代码单元通常包括：

- 一个函数
- 一个类
- 一个独立算法模块

特点：

- 不需要启动完整自动驾驶系统。
- 不需要真实传感器。
- 不需要连接真实底盘。
- 可以直接构造输入数据。
- 自动检查输出是否符合预期。

例如，测试一个障碍物距离计算函数。

## 2.2 Python 单元测试框架 pytest

安装：

```bash
pip3 install pytest
```

项目结构：

```text
unit_test_demo/
├── obstacle.py
└── tests/
    └── test_obstacle.py
```

### 业务代码 obstacle.py

```python
def calculate_ttc(distance, relative_speed):

    if distance < 0:
        raise ValueError("距离不能为负数")

    if relative_speed <= 0:
        return float('inf')

    return distance / relative_speed
```

### 测试代码 test_obstacle.py

```python
import pytest

from obstacle import calculate_ttc


def test_ttc_normal():

    result = calculate_ttc(20, 5)

    assert result == 4


def test_ttc_zero_speed():

    result = calculate_ttc(20, 0)

    assert result == float('inf')


def test_ttc_negative_speed():

    result = calculate_ttc(20, -2)

    assert result == float('inf')


def test_ttc_negative_distance():

    with pytest.raises(ValueError):

        calculate_ttc(-10, 5)
```

运行测试：

```bash
cd unit_test_demo

python3 -m pytest -v
```

结果：

```text
test_ttc_normal PASSED
test_ttc_zero_speed PASSED
test_ttc_negative_speed PASSED
test_ttc_negative_distance PASSED
```

含义：

- PASSED：测试通过。
- FAILED：测试失败。
- ERROR：测试执行过程中发生错误。

## 2.3 Assert 断言

`assert` 用于判断实际结果是否符合预期。

```python
result = calculate_ttc(20, 5)

assert result == 4
```

如果结果等于 4，测试通过。

如果结果不等于 4，测试失败。

常用断言：

| 断言 | 含义 |
|---|---|
| assert a == b | 判断两个值相等 |
| assert a != b | 判断两个值不相等 |
| assert a > b | 判断 a 大于 b |
| assert a < b | 判断 a 小于 b |
| assert condition | 判断条件为真 |
| pytest.raises() | 判断是否抛出指定异常 |

## 2.4 参数化测试

使用一段测试代码测试多组输入。

```python
import pytest

@pytest.mark.parametrize(
    "distance,speed,expected",
    [
        (20, 5, 4),
        (10, 2, 5),
        (30, 10, 3),
        (100, 20, 5),
    ]
)
def test_ttc(distance, speed, expected):

    result = calculate_ttc(distance, speed)

    assert result == expected
```

适用场景：

- 不同障碍物距离。
- 不同车辆速度。
- 不同 GNSS 坐标。
- 不同雷达置信度。
- 不同 PID 输入。

## 2.5 自动驾驶常见单元测试

| 模块 | 测试内容 |
|---|---|
| GNSS | BLH 转 ENU、坐标方向 |
| 感知 | 障碍物过滤、置信度筛选 |
| 融合 | 时间戳匹配、坐标转换 |
| 决策 | 停车条件、状态切换 |
| 规划 | 路径长度、曲率、碰撞检测 |
| 控制 | PID 输出、速度限幅 |
| 安全 | 急停逻辑、异常数据处理 |

# 三、集成测试（Integration Test）

## 3.1 什么是集成测试

集成测试是将多个独立模块组合起来，验证模块之间的数据传递、接口调用和业务逻辑是否正确。

重点不再是单个函数，而是模块之间的协作。

例如：

毫米波雷达 → 感知 → 决策 → 底盘控制 → 车辆停车。

需要验证：

1. 上一个模块能否正常发布数据。
2. 下一个模块能否正常接收数据。
3. 消息类型和数据格式是否一致。
4. 坐标系和时间戳是否正确。
5. 数据处理结果是否符合预期。
6. 最终控制指令是否正确。

## 3.2 自动驾驶集成测试架构

```text
┌──────────────────────────┐
│       毫米波雷达节点      │
│                          │
│ Topic: /radar/objects    │
│ 发布障碍物信息            │
└────────────┬─────────────┘
             │
             ▼
┌──────────────────────────┐
│        感知处理节点       │
│                          │
│ 目标过滤、数据处理        │
│                          │
│ Topic: /perception/obstacles
└────────────┬─────────────┘
             │
             ▼
┌──────────────────────────┐
│         决策节点          │
│                          │
│ TTC 计算、停车判断        │
│                          │
│ Topic: /decision/cmd     │
└────────────┬─────────────┘
             │
             ▼
┌──────────────────────────┐
│        底盘控制节点       │
│                          │
│ 速度控制、制动控制        │
│                          │
│ Topic: /cmd_vel 或 CAN   │
└────────────┬─────────────┘
             │
             ▼
┌──────────────────────────┐
│         车辆底盘          │
│                          │
│ 减速、制动、停车           │
└──────────────────────────┘
```

## 3.3 集成测试的具体内容

### 第一阶段：雷达到感知

测试内容：

- 雷达节点是否正常运行。
- 雷达 Topic 是否正常发布。
- 感知节点是否订阅成功。
- 消息类型是否一致。
- 障碍物位置是否正确。
- 无效目标是否被过滤。

### 第二阶段：感知到决策

测试内容：

- 决策节点是否收到障碍物数据。
- 坐标系是否正确。
- 障碍物距离是否正确。
- TTC 是否正确计算。
- 是否满足停车条件。
- 是否正确发布 STOP。

### 第三阶段：决策到底盘控制

测试内容：

- 控制节点是否订阅决策 Topic。
- 是否正确接收到 STOP。
- 是否设置目标速度为 0。
- 是否正确生成制动指令。
- CAN 指令是否成功发送。

### 第四阶段：底盘实际执行

测试内容：

- 底盘是否收到制动指令。
- 制动反馈是否正常。
- 实际速度是否逐渐下降。
- 车辆是否真正停止。
- 是否存在异常延迟。

注意：目标速度为 0 不代表车辆实际速度已经为 0。

# 四、ROS 通信测试

ROS Noetic 中，可以通过命令行检查节点、Topic 和消息。

## 4.1 启动 ROS Master

```bash
roscore
```

## 4.2 查看 ROS 节点

```bash
rosnode list
```

示例：

```text
/radar_node
/perception_node
/decision_node
/chassis_node
```

注意：节点存在不代表节点之间的数据通信正常。

## 4.3 查看 Topic

```bash
rostopic list
```

示例：

```text
/radar/objects
/perception/obstacles
/decision/cmd
/cmd_vel
```

## 4.4 查看 Topic 类型

```bash
rostopic type /radar/objects
```

## 4.5 查看 Topic 发布者和订阅者

```bash
rostopic info /radar/objects
```

示例：

```text
Type: custom_msgs/RadarObjects

Publishers:
 * /radar_node

Subscribers:
 * /perception_node
```

表示：

- 雷达节点正在发布数据。
- 感知节点正在订阅数据。

## 4.6 查看实时消息

```bash
rostopic echo /radar/objects
```

## 4.7 查看 Topic 发布频率

```bash
rostopic hz /radar/objects
```

## 4.8 查看消息延迟

```bash
rostopic delay /radar/objects
```

## 4.9 查看 ROS 节点连接关系

```bash
rqt_graph
```

可以直观查看：

- 哪些节点正在运行。
- 哪些节点发布 Topic。
- 哪些节点订阅 Topic。
- 节点之间的通信关系。

注意：rqt_graph 主要展示 ROS 通信拓扑，不能证明业务处理结果正确。

# 五、ROS 自动化集成测试

## 5.1 什么是自动化集成测试

人工测试：

```text
启动节点
→ 发布雷达数据
→ 查看感知结果
→ 查看决策结果
→ 查看底盘指令
```

自动化测试：

```text
启动测试程序
→ 自动发布模拟雷达数据
→ 自动检查感知输出
→ 自动检查决策输出
→ 自动检查控制指令
→ 输出 PASS / FAILED
```

测试程序相当于一个自动化测试人员。

## 5.2 自动化测试架构

```text
            测试节点
                │
                ▼
          模拟雷达数据
                │
                ▼
          感知处理节点
                │
                ▼
            决策节点
                │
                ▼
          底盘控制节点
                │
                ▼
           模拟底盘节点
                │
                ▼
           检查测试结果
                │
                ▼
          PASS / FAILED
```

## 5.3 模拟雷达数据

假设测试环境中的 Topic 使用：

```text
std_msgs/String
```

发布测试数据：

```bash
rostopic pub -r 10 /radar/objects std_msgs/String \
"data: 'distance=3.0,speed=-2.0'"
```

表示：

- 障碍物距离 3 米。
- 相对速度 -2 m/s。
- 每秒发布 10 次。

注意：这是演示接口，真实项目必须按照实际消息类型和字段构造数据。

## 5.4 Python ROS 自动化测试示例

文件：

```text
test_truck_integration.py
```

代码：

```python
#!/usr/bin/env python3

import rospy
import unittest

from std_msgs.msg import String
from std_msgs.msg import Float32


class TruckIntegrationTest(unittest.TestCase):

    def setUp(self):

        rospy.init_node(
            "truck_integration_test",
            anonymous=True
        )

        self.decision = None
        self.target_speed = None

        self.radar_pub = rospy.Publisher(
            "/radar/objects",
            String,
            queue_size=10
        )

        rospy.Subscriber(
            "/decision/cmd",
            String,
            self.decision_callback
        )

        rospy.Subscriber(
            "/vehicle/commanded_speed",
            Float32,
            self.speed_callback
        )

        rospy.sleep(1)

    def decision_callback(self, msg):

        self.decision = msg.data

    def speed_callback(self, msg):

        self.target_speed = msg.data

    def test_emergency_stop(self):

        # 模拟前方3米存在障碍物
        msg = String()

        msg.data = "distance=3.0,speed=-2.0"

        # 发布雷达数据
        self.radar_pub.publish(msg)

        # 等待停车决策
        deadline = rospy.Time.now() + rospy.Duration(5)

        rate = rospy.Rate(20)

        while not rospy.is_shutdown():

            if self.decision == "STOP":
                break

            if rospy.Time.now() > deadline:
                self.fail("决策节点没有输出STOP")

            rate.sleep()

        # 验证决策结果
        self.assertEqual(
            self.decision,
            "STOP"
        )

        # 验证底盘目标速度
        self.assertIsNotNone(self.target_speed)

        self.assertAlmostEqual(
            self.target_speed,
            0.0,
            places=2
        )


if __name__ == "__main__":

    unittest.main()
```

注意：

这段代码是教学示例，真实项目还需要根据消息接口进行适配，并增加：

- 节点启动检查。
- 订阅连接检查。
- 数据时间戳检查。
- 测试数据序列号。
- 旧消息清理。
- 感知输出检查。
- 底盘反馈检查。

另外，测试程序应该在 ROS 节点启动完成后再注入数据。

## 5.5 使用 rostest

ROS 提供 rostest，可以通过 Launch 文件启动多个节点和测试程序。

项目结构：

```text
decision/
├── launch/
│   └── integration_test.launch
│
├── scripts/
│   ├── perception_node.py
│   ├── decision_node.py
│   └── mock_chassis.py
│
└── test/
    └── test_truck_integration.py
```

Launch 文件：

```xml
<launch>

    <!-- 感知节点 -->
    <node pkg="decision"
          type="perception_node.py"
          name="perception_node"
          output="screen"/>

    <!-- 决策节点 -->
    <node pkg="decision"
          type="decision_node.py"
          name="decision_node"
          output="screen"/>

    <!-- 模拟底盘 -->
    <node pkg="decision"
          type="mock_chassis.py"
          name="chassis_node"
          output="screen"/>

    <!-- 自动化测试 -->
    <test pkg="decision"
          type="test_truck_integration.py"
          name="integration_test"
          time-limit="30"/>

</launch>
```

运行：

```bash
rostest decision integration_test.launch
```

实际工程中需要在 CMakeLists.txt、package.xml 中配置 rostest 依赖和测试文件安装规则。

# 六、ROS Bag 回放测试

## 6.1 什么是 ROS Bag

ROS Bag 是 ROS 中用于记录和回放 Topic 消息的工具。

可以将实车运行过程中的数据保存下来，以后反复回放。

例如：

```bash
rosbag record -a
```

记录当前 ROS 系统中所有可录制的 Topic。

回放：

```bash
rosbag play truck_test.bag
```

## 6.2 Bag 回放测试流程

```text
实车采集数据
      │
      ▼
  ROS Bag 文件
      │
      ▼
  rosbag play
      │
      ▼
  感知处理节点
      │
      ▼
    决策节点
      │
      ▼
  检查输出结果
```

## 6.3 Bag 回放的优势

- 不需要每次都开车采集数据。
- 可以重复测试同一组输入。
- 可以对比算法修改前后的效果。
- 可以进行历史问题复现。
- 可以用于回归测试。

## 6.4 注意事项

回放测试需要关注：

- 时间戳是否正确。
- 是否需要使用 `/use_sim_time`。
- 是否需要发布 `/clock`。
- Topic 是否存在名称冲突。
- 数据回放速度是否合适。
- 是否有多个节点重复发布相同 Topic。

Bag 回放不能代替真实车辆的制动性能测试。

# 七、自动驾驶测试用例设计

集成测试不能只测试正常情况，还要覆盖异常情况。

| 编号 | 测试场景 | 输入条件 | 预期结果 |
|---|---|---|---|
| TC01 | 正常行驶 | 前方无障碍物 | 正常行驶 |
| TC02 | 远距离障碍物 | 前方20m有障碍物 | 根据安全策略决定 |
| TC03 | 近距离障碍物 | 前方3m有障碍物 | 触发停车 |
| TC04 | 后方障碍物 | 后方存在障碍物 | 不误触发前向停车 |
| TC05 | 雷达断开 | 雷达停止发布 | 检测通信异常 |
| TC06 | 雷达数据过期 | 时间戳长期不更新 | 进入安全策略 |
| TC07 | 感知节点崩溃 | 感知停止发布 | 决策检测异常 |
| TC08 | 决策节点崩溃 | 决策停止发布 | 安全监控机制触发 |
| TC09 | 底盘通信中断 | 控制指令无法送达 | 检测执行失败 |
| TC10 | 障碍物消失 | 雷达不再检测到障碍物 | 按策略解除停车 |

## 7.1 正常测试

验证正常输入下系统能否完成预期功能。

## 7.2 边界测试

例如：

- 障碍物距离刚好等于安全距离。
- TTC 刚好等于停车阈值。
- 车辆速度刚好等于最大速度。
- 坐标刚好处于规划边界。

## 7.3 异常测试

例如：

- 雷达数据为空。
- GNSS 数据异常。
- 传感器时间戳过期。
- ROS 节点崩溃。
- CAN 通信中断。
- 底盘反馈异常。

## 7.4 故障注入测试

人为制造故障，检查系统能否进入安全状态。

例如：

- 关闭雷达节点。
- 杀死感知节点。
- 中断决策节点通信。
- 模拟 CAN 超时。
- 发布错误坐标。
- 发布过期数据。

注意：故障注入应优先在仿真或隔离测试环境中进行。真实车辆测试必须具备独立安全措施。

# 八、系统测试（System Test）

## 8.1 什么是系统测试

系统测试是对完整软件系统进行测试。

不仅验证模块之间的通信，还要验证完整系统能否实现设计功能。

例如自动驾驶矿卡：

- 定位是否准确。
- 感知是否正常。
- 决策是否正确。
- 规划是否合理。
- 控制是否稳定。
- 车辆能否完成自动驾驶任务。

## 8.2 系统测试主要内容

| 测试类型 | 测试内容 |
|---|---|
| 功能测试 | 自动驾驶任务能否完成 |
| 性能测试 | CPU、内存、运行频率 |
| 实时性测试 | 感知和控制延迟 |
| 稳定性测试 | 长时间运行是否异常 |
| 安全测试 | 故障时能否进入安全状态 |
| 实车测试 | 真实车辆运行效果 |

## 8.3 仿真测试与实车测试

仿真测试：

- 构造虚拟车辆。
- 构造虚拟障碍物。
- 模拟不同道路环境。
- 验证规划和决策效果。

实车测试：

- 真实传感器。
- 真实车辆底盘。
- 真实通信接口。
- 真实制动执行。
- 验证实际运行效果。

---

# 九、测试覆盖率与回归测试

## 9.1 代码覆盖率

代码覆盖率用于衡量测试执行过程中代码被执行的情况。

常见指标：

| 指标 | 含义 |
|---|---|
| 行覆盖率 | 有多少代码行被执行 |
| 分支覆盖率 | 有多少判断分支被执行 |
| 函数覆盖率 | 有多少函数被调用 |

安装：

```bash
pip3 install coverage
```

执行：

```bash
coverage run -m pytest
```

查看报告：

```bash
coverage report -m
```

生成 HTML 报告：

```bash
coverage html
```

注意：

覆盖率高不代表代码一定正确。

还必须检查测试输入、预期输出和边界条件。

## 9.2 回归测试（Regression Test）

回归测试是修改代码后，重新执行之前的测试，确认原有功能没有受到破坏。

例如：

第一次版本：

```text
障碍物过滤算法 V1
测试全部通过
```

修改算法：

```text
障碍物过滤算法 V2
```

重新执行原来的测试：

```text
测试用例1：PASS
测试用例2：PASS
测试用例3：FAILED
```

说明新版本可能破坏了原有功能。

自动驾驶中常见的回归测试：

- 感知算法更新后重新跑历史 Bag。
- 决策阈值修改后重新测试停车逻辑。
- 规划算法修改后重新测试历史路径。
- 控制参数修改后重新验证速度响应。

# 十、Mock 模拟测试

## 10.1 什么是 Mock

Mock 可以理解为用模拟模块代替真实模块。

例如：

真实系统：

```text
毫米波雷达 → 感知 → 决策 → CAN 底盘
```

测试系统：

```text
模拟雷达 → 感知 → 决策 → 模拟底盘
```

这样不需要真实传感器和底盘，也可以测试软件链路。

## 10.2 常见 Mock 对象

| 真实模块 | 模拟对象 |
|---|---|
| 毫米波雷达 | 模拟障碍物数据 |
| GNSS | 模拟经纬度 |
| IMU | 模拟姿态数据 |
| 相机 | 模拟目标检测结果 |
| CAN | 模拟控制接口 |
| 底盘 | 模拟车辆速度反馈 |

## 10.3 Mock 的作用

- 降低测试成本。
- 不依赖真实硬件。
- 方便构造异常输入。
- 方便重复测试。
- 提高自动化测试效率。

注意：

Mock 只能验证软件对模拟输入的处理逻辑，不能证明真实硬件正常。

# 十一、CI 持续集成

## 11.1 什么是 CI

CI（Continuous Integration，持续集成）是自动化软件开发流程。

例如：

开发人员修改代码并提交 Git。

```bash
git add .
git commit -m "modify obstacle decision"
git push
```

服务器自动执行：

```text
代码提交
   │
   ▼
自动拉取代码
   │
   ▼
编译项目
   │
   ▼
执行单元测试
   │
   ▼
执行集成测试
   │
   ▼
生成测试报告
```

如果测试失败，就通知开发人员。

## 11.2 自动驾驶项目中的 CI

可以自动完成：

- Python 代码检查。
- C++ 编译。
- pytest 测试。
- GTest 测试。
- ROS 集成测试。
- 代码覆盖率统计。
- 测试报告生成。

常见工具：

- GitLab CI
- GitHub Actions
- Jenkins
- CMake
- pytest
- GoogleTest

CI 不能替代仿真和实车测试。

# 十五、核心知识总结

| 概念 | 通俗理解 |
|---|---|
| Unit Test | 测试一个函数或模块 |
| Test Case | 一组测试输入和预期结果 |
| Assert | 判断结果是否符合预期 |
| Mock | 用模拟模块代替真实模块 |
| Integration Test | 测试多个模块之间的协作 |
| System Test | 测试整个系统 |
| Regression Test | 修改代码后重新测试旧功能 |
| Coverage | 代码覆盖率 |
| CI | 自动编译和执行测试 |
| ROS Bag | 记录和回放 ROS 数据 |
| rostest | ROS 自动化测试工具 |

> [!important] 最重要的理解
>
> - 单元测试：单个功能能不能正确工作？
> - 集成测试：各个模块能不能正确连接、传递数据和协同工作？
> - 系统测试：完整自动驾驶系统能不能完成任务？
> - 实车测试：真实车辆能不能安全、稳定地执行任务？
>
> 自动驾驶软件测试不能只验证程序有没有报错，还要验证数据正确性、时序、异常处理和最终执行效果。

# 十六、实践任务：构建矿卡自动停车集成测试

建议最终完成以下项目：

**测试目标：**

模拟毫米波雷达检测到车辆前方障碍物，自动验证系统能否完成停车决策和控制指令输出。

**测试链路：**

```text
模拟毫米波雷达
       ↓
真实感知处理节点
       ↓
真实决策节点
       ↓
真实控制逻辑节点
       ↓
模拟底盘节点
       ↓
自动测试报告
```

**验收标准：**

- [ ] 模拟雷达数据能够正常发布。
- [ ] 感知节点能够接收数据。
- [ ] 感知输出的障碍物信息正确。
- [ ] 决策节点能够接收障碍物。
- [ ] TTC 计算结果正确。
- [ ] 决策节点正确输出 STOP。
- [ ] 控制节点收到 STOP。
- [ ] 模拟底盘收到停车指令。
- [ ] 模拟底盘速度逐渐下降至 0。
- [ ] 测试程序自动判断 PASS 或 FAILED。
- [ ] 能够生成测试结果报告。

**最终目标：**

实现一套可以反复运行的 ROS 自动化集成测试程序，不依赖真实毫米波雷达和真实底盘，就能验证自动驾驶软件链路的基本功能。

真实车辆制动、安全响应和故障保护仍需在独立的仿真、硬件在环及受控实车测试中验证。
